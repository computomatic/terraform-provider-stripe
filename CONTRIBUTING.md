# Contributing

The provider's design is in `adrs/`, starting with `adrs/1-pending/2026-10-17-provider-architecture/ADR.md`. It covers generation, resource mapping, configuration, the API version, the client, testing and naming.

## Build and test

```sh
go build ./...
go vet ./...
go test ./...
```

## Generated code

`spec/openapi.json` is the pinned Stripe OpenAPI spec (`spec/PIN.json` records its tag, commit and hash). `tools/schemagen` turns it into the field tables under `internal/generated` and into `internal/stripeapi/version.go`. After changing the spec, the pin, the generator or the list of resources in `tools/schemagen/resources.go`, regenerate and commit the result:

```sh
go generate ./internal/generated
```

`go test ./...` fails when a generated file is out of date. `tools/schemadiff old.json new.json` compares two `terraform providers schema -json` documents and marks breaking changes.

## Adding a resource

A resource is a short declaration in `internal/resources/<name>` that the generic engine in `internal/engine` turns into a resource and a data source. Each resource directory needs:

- its declaration, with a `Description` that says what `terraform destroy` does and anything else a user must know, a `DataSourceDescription` that says only what the object is (a data source destroys and imports nothing), and an `ImportNote` (with `ImportNoteLevel` `engine.NoteWarning` for a consequence) when an imported object differs from a configured one;
- `examples/resources/stripe_<name>/resource.tf` and `import.sh`, whose last line is `terraform import stripe_<name>.<name> <id>` with a `<parent_id>/<id>` ID for a resource with a `Parent`, and `examples/data-sources/stripe_<name>/data-source.tf` when it has a data source;
- the six acceptance tests `TestAcc<Name>_{create,update,replace,import,delete,drift}`;
- its regenerated pages under `docs/`.

A read-only object, such as the balance or the tax code catalogue, has a `datasource.go`, a data source example and one `TestAcc<Name>_read` instead. `internal/resources` checks the declaration, the examples and the tests.

## Docs

The pages under `docs/` are generated by `tools/docgen` from the provider's schema, the examples under `examples/` and the provider page's prose in `docs-src/provider.md`. Never edit them by hand. Regenerate them after any change to a schema, a description or an example, and commit the result with the change:

```sh
go generate ./...
```

Generation needs no Terraform or OpenTofu binary. `scripts/check-docs.sh` regenerates and fails when `docs/` changed. Run it before you push.

## Acceptance tests

Tests that need a Stripe API run against a Stripe API fake, one fresh account per test, and are skipped when no fake is configured. The fake is not yet public, so you cannot run these tests yourself. CI runs them on pushes and on pull requests from branches of this repository; maintainers run them for pull requests from forks. Unit tests and the docs check run for everyone. Set `STRIPE_FAKE_SOURCE` to the fake's source tree and the harness builds it from a temporary copy and starts it, or set `STRIPE_FAKE_URL` (and `STRIPE_FAKE_ADMIN_TOKEN` if it needs one) to use a running fake.

They use terraform-plugin-testing and need `TF_ACC=1`:

```sh
TF_ACC=1 STRIPE_FAKE_SOURCE=<fake source> go test ./internal/resources/...
```

They run with the `terraform` on the path. To run them with OpenTofu, also set `TF_ACC_TERRAFORM_PATH=$(which tofu)`, `TF_ACC_PROVIDER_NAMESPACE=hashicorp` and `TF_ACC_PROVIDER_HOST=registry.opentofu.org`.

### Real-Stripe mode

The same tests can run against a Stripe sandbox, which maintainers do for smoke runs. Set `TF_SMOKE=1` and `STRIPE_API_KEY` to an `sk_test_` key; do not set any `STRIPE_FAKE_*` variable, the harness refuses both together. Only the maintainers' sandbox run does this: never run it locally.

In this mode every test shares the one account, and the key stays in the environment, out of generated HCL. A test written for both modes:

- passes every display name through `acct.Name(base)`, every chosen ID through `acct.ID(prefix, base)` and every other value Stripe keeps unique (lookup keys, meter event names) through `acct.Unique(base)`. In smoke mode they gain a `tfsmoke-<run id>-` prefix and the latter two fail the test when a different test asks for the same value, because archived objects keep their keys, so give each test its own base. Against the fake they return the base unchanged;
- calls `acctest.RequireFake(t)` before `acctest.RequestLog` or `acctest.Seed`, or checks `acct.Smoke` before them, and assumes no fresh account (an empty list, a zero balance). A test that skips this fails `TestWave1FakeOnlyCallsAreGuarded`.

Issuing and Treasury run on a connected account. Their tests get one from `tfacc.IssuingAccount`, which returns its configuration: `ConnectedProviderBlock` renders a second provider block, aliased `connected`, whose `stripe_account` is that account, and `tfacc.Client` on it sends the `Stripe-Account` header. Stripe verifies a new connected account for minutes, so in smoke mode the helper reuses one tagged `metadata[tfacc_role]=issuing` and never deletes it. The fake's request log does not hold the requests made through `Stripe-Account`, so these tests cannot assert on it.

Stripe makes some objects in the background, such as credit balance transactions, meter event summaries and active entitlements, and lists them a moment, or up to a minute, after their cause. A test waits for them with `tfacc.AwaitListed` before it reads one. The fake makes them at once.

## CI

CI (`.github/workflows/ci.yml`) runs the checks as the `unit` job, the docs check (`scripts/check-docs.sh`) as the `docs` job, and the acceptance tests as the `acceptance` job, under Terraform and then OpenTofu, against the released fake image named by `.fake-version`. To move to a newer fake, change that one line. The `acceptance` job is skipped for pull requests from forks, because the fake image is private.

## Trying a build against the fake

Start the fake Stripe API with `-default-account-key sk_test_<anything>`, then point `base_url` at it:

```hcl
provider "stripe" {
  api_key  = "sk_test_<anything>"
  base_url = "http://127.0.0.1:12111"
}
```

To use a local build, `go install .` and add a `dev_overrides` entry for `registry.terraform.io/computomatic/stripe` in a CLI configuration file selected with `TF_CLI_CONFIG_FILE`.

## Clean room

Never copy source from `stripe/terraform-provider-stripe` or `lukasaron/terraform-provider-stripe`. Derive code from Stripe's public API docs and OpenAPI spec.

## Releasing

Releases are cut from `main`. Tag the commit `vX.Y.Z` and push the tag:

```sh
git tag vX.Y.Z
git push origin vX.Y.Z
```

The release workflow builds the provider for each supported platform, signs the checksums and publishes a GitHub release. The Terraform Registry picks the release up from there. Move the changelog's Unreleased entries under the new version before tagging.
